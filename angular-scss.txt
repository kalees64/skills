# Enterprise Frontend Architecture & Design Standard

This skill defines the mandatory standards for building production-grade SaaS interfaces intended for high-scale environments (millions to billions of users).

The objective is to deliver:

- Scalable architecture
- Long-term maintainability
- Performance at scale
- Accessibility compliance
- Test-driven reliability
- Distinct, brand-defining design quality

Every implementation must meet enterprise engineering standards.

---

# 1. NON-NEGOTIABLE ENGINEERING REQUIREMENTS

## 1.1 Framework & Platform Standard

- Framework: **Angular v17+ (latest LTS)**
- Language: **TypeScript (strict mode)**
- Component Model: **Standalone Components** (default — no NgModules unless legacy migration)
- Rendering Strategy: Choose appropriately (SSR via Angular Universal / `@angular/ssr`, SSG, CSR) based on scalability and performance needs.
- State Management: **Angular Signals** (primary) or **NgRx Signal Store** for complex global state
- Styling: **SCSS** with design tokens
- No alternative frameworks.

---

## 1.2 Architectural Discipline

All implementations must follow:

### SOLID Principles

- Single Responsibility
- Open/Closed
- Liskov Substitution
- Interface Segregation
- Dependency Inversion

### ACID-Inspired Frontend Consistency

- Atomic component design
- Isolated logic
- Predictable state management via Signals
- Deterministic rendering behavior
- Durable and extensible patterns

### Separation of Concerns

Clear modular boundaries:
```
/core               ← singleton services, guards, interceptors, app config
/shared             ← reusable standalone components, pipes, directives
/features           ← feature folders (lazy-loaded via routing)
/models             ← interfaces and type definitions
/services           ← data access and business logic services
/utils              ← pure utility functions
/styles             ← global styles, SCSS tokens, variables, mixins
/__tests__          ← unit and integration tests
```

Requirements:

- All components must be **Standalone** by default
- No business logic inside presentational components
- No direct HTTP calls inside UI components
- All HTTP calls must go through dedicated Angular Services using `HttpClient`
- Use `inject()` function instead of constructor injection
- Lazy-load all feature routes via Angular Router `loadComponent` / `loadChildren`
- Clear dependency direction enforced via feature boundaries

---

## 1.3 Modern Angular APIs (MANDATORY — v17+)

### Standalone Components
```typescript
@Component({
  selector: 'app-user-card',
  standalone: true,
  imports: [CommonModule, RouterLink],
  templateUrl: './user-card.component.html',
  changeDetection: ChangeDetectionStrategy.OnPush,
})
export class UserCardComponent {}
```

### Dependency Injection via `inject()`
```typescript
// ✅ CORRECT — use inject() function
export class UserCardComponent {
  private userService = inject(UserService);
  private router = inject(Router);
}

// ❌ WRONG — avoid constructor injection in new code
constructor(private userService: UserService) {}
```

### Application Bootstrap
```typescript
// main.ts
bootstrapApplication(AppComponent, {
  providers: [
    provideRouter(routes),
    provideHttpClient(withInterceptors([authInterceptor])),
    provideAnimationsAsync(),
  ]
});
```

---

## 1.4 Code Quality Standards

- Strict TypeScript (no `any`)
- Fully typed props, responses, services, and utilities
- No dead code
- No `console.log` in production code
- Clean imports using path aliases (`@core`, `@shared`, `@features`)
- Change detection strategy: **OnPush** for all components
- Use `trackBy` equivalent inside `@for` blocks (built-in `track` expression)
- Unsubscribe from Observables using `takeUntilDestroyed()` or `async` pipe
- Prefer **Signals** over RxJS for local component state
- Error handling via Angular `ErrorHandler`
- Defensive programming mindset

# 2. MODERN TEMPLATE CONTROL FLOW SYNTAX (MANDATORY — Angular v17+)

Angular v17 introduced a **built-in control flow syntax** that replaces structural directives. All new code must use this syntax exclusively.

---

## 2.1 @if / @else if / @else

Replaces `*ngIf`.
```html
<!-- ✅ CORRECT -->
@if (user.isAdmin) {
  <app-admin-panel />
} @else if (user.isModerator) {
  <app-moderator-panel />
} @else {
  <app-user-panel />
}

<!-- ❌ WRONG — never use in new code -->
<app-admin-panel *ngIf="user.isAdmin; else userPanel" />
<ng-template #userPanel><app-user-panel /></ng-template>
```

---

## 2.2 @for / track

Replaces `*ngFor`. The `track` expression is **mandatory** — it replaces `trackBy` and is enforced by the compiler.
```html
<!-- ✅ CORRECT -->
@for (product of products(); track product.id) {
  <app-product-card [product]="product" />
} @empty {
  <p>No products available.</p>
}

<!-- ❌ WRONG — never use in new code -->
<app-product-card
  *ngFor="let product of products; trackBy: trackById"
  [product]="product"
/>
```

---

## 2.3 @switch / @case / @default

Replaces `[ngSwitch]`.
```html
<!-- ✅ CORRECT -->
@switch (order.status) {
  @case ('pending') {
    <app-pending-badge />
  }
  @case ('shipped') {
    <app-shipped-badge />
  }
  @default {
    <app-default-badge />
  }
}

<!-- ❌ WRONG — never use in new code -->
<ng-container [ngSwitch]="order.status">
  <app-pending-badge *ngSwitchCase="'pending'" />
</ng-container>
```

---

## 2.4 @let — Template Variable Declaration (Angular v18+)

Replaces `*ngIf as` aliasing patterns. Use `@let` to declare and reuse template-local variables.
```html
<!-- ✅ CORRECT — compute once, reuse -->
@let fullName = user.firstName + ' ' + user.lastName;
@let isEligible = user.age >= 18 && user.isVerified;

<h2>Welcome, {{ fullName }}</h2>

@if (isEligible) {
  <app-eligibility-badge [name]="fullName" />
}

<!-- ✅ Use with async data -->
@let userData = userSignal();
@if (userData) {
  <app-profile [user]="userData" />
}
```

Rules for `@let`:

- Scoped to the current template block and its children
- Cannot be reassigned after declaration
- Ideal for derived values, async unwrapping, and long expression aliasing
- Replaces `as` aliasing in `*ngIf` and `async` pipe patterns

---

## 2.5 @defer — Deferred Loading (Angular v17+)

Use `@defer` for lazy rendering of heavy components to improve initial load performance.
```html
<!-- Basic defer -->
@defer {
  <app-heavy-dashboard />
} @placeholder {
  <p>Loading dashboard...</p>
} @loading (minimum 300ms) {
  <app-spinner />
} @error {
  <p>Failed to load. Please retry.</p>
}

<!-- Defer on interaction -->
@defer (on interaction) {
  <app-comments-section />
} @placeholder {
  <button>Show Comments</button>
}

<!-- Defer on viewport -->
@defer (on viewport) {
  <app-analytics-chart />
} @placeholder {
  <div class="chart-skeleton" />
}

<!-- Defer on idle -->
@defer (on idle) {
  <app-recommendations />
}

<!-- Defer with prefetch -->
@defer (on viewport; prefetch on idle) {
  <app-product-details />
}
```

Defer trigger options:

- `on idle` — when browser is idle
- `on viewport` — when block enters viewport
- `on interaction` — on user click or focus
- `on hover` — on mouse hover
- `on immediate` — as soon as possible (non-blocking)
- `on timer(2s)` — after a time delay
- `when condition` — when a boolean expression is true

# 3. SIGNALS — REACTIVE STATE (MANDATORY — Angular v17+)

Signals are the **primary** reactive primitive. Use RxJS only for async streams (HTTP, WebSockets).

## 3.1 Core Signal APIs
```typescript
import { signal, computed, effect, input, output, model } from '@angular/core';

// Writable signal
const count = signal(0);

// Read
console.log(count());

// Update
count.set(5);
count.update(val => val + 1);

// Computed (derived, read-only)
const doubled = computed(() => count() * 2);

// Effect (side effects on signal change)
effect(() => {
  console.log('Count changed:', count());
});
```

---

## 3.2 Component Inputs as Signals — `input()`
```typescript
// ✅ CORRECT — Signal-based inputs (Angular v17.1+)
export class ProductCardComponent {
  product = input.required<Product>();
  variant = input<'default' | 'compact'>('default');

  // Derived from input signal
  displayPrice = computed(() =>
    this.product().price.toFixed(2)
  );
}

// ❌ WRONG — avoid @Input() decorator in new code
@Input() product!: Product;
```

---

## 3.3 Component Outputs — `output()`
```typescript
// ✅ CORRECT — output() function (Angular v17.3+)
export class ProductCardComponent {
  addToCart = output<Product>();

  onAdd() {
    this.addToCart.emit(this.product());
  }
}

// ❌ WRONG — avoid @Output() + EventEmitter in new code
@Output() addToCart = new EventEmitter<Product>();
```

---

## 3.4 Two-Way Binding — `model()`
```typescript
// ✅ CORRECT — model() signal for two-way binding (Angular v17.2+)
export class QuantitySelectorComponent {
  value = model<number>(1);

  increment() {
    this.value.update(v => v + 1);
  }
}

// In parent template
<app-quantity-selector [(value)]="cartItemQty" />
```

---

## 3.5 `toSignal` / `toObservable` — RxJS Interop
```typescript
import { toSignal, toObservable } from '@angular/core/rxjs-interop';

// Convert Observable to Signal
const users = toSignal(this.userService.getAll$(), { initialValue: [] });

// Convert Signal to Observable
const count$ = toObservable(this.count);
```

# 4. ACCESSIBILITY & SEMANTIC HTML (MANDATORY)

Accessibility is not optional.

## 4.1 Semantic Structure

Use semantic HTML elements:

- `<main>`, `<section>`, `<article>`, `<nav>`
- `<header>`, `<footer>`, `<aside>`
- `<form>`, `<button>`, `<fieldset>`, `<legend>`

Avoid non-semantic containers when a semantic alternative exists.

---

## 4.2 ARIA & Identifiers

Requirements:

- Every `<section>` must include `aria-label`
- Every interactive element must include a unique `id` and `aria-label`
- IDs must be content-specific and context-aware — never generic (`btn1`, `section2`)
- Use Angular CDK `A11yModule` for focus management and live region announcements

---

## 4.3 Accessibility Compliance

Must ensure:

- Proper heading hierarchy (h1 → h6)
- Keyboard navigability
- Visible focus states
- Screen reader compatibility
- No div-based interactive elements
- ARIA only when necessary (not overused)
- WCAG 2.1 AA compliant design decisions

---

# 5. MANDATORY UNIT TESTING

No module may exist without corresponding tests.

## 5.1 Required Stack

- **Jest** (preferred) or Karma + Jasmine
- **Angular Testing Library** or `TestBed`
- **Spectator** (optional, for reduced boilerplate)

---

## 5.2 Coverage Requirements

Test the following:

- Component rendering and template behavior
- Signal input / output / model behavior
- `@if`, `@for`, `@switch` template branch coverage
- User interactions (clicks, form submissions)
- Edge cases and empty states (`@empty` block)
- Service logic (with `HttpClientTestingModule` / `provideHttpClientTesting()`)
- NgRx Signal Store actions and computed state
- Guard and interceptor behavior
- Pipe and directive logic

Use the AAA pattern:

- Arrange
- Act
- Assert

Target mindset: minimum **80% meaningful coverage**.

Tests must validate behavior — not implementation details.

# 6. SaaS-Level Design System Philosophy

## 6.1 Design Direction

Before implementation, clearly define product context and choose an intentional aesthetic strategy:

- Refined enterprise minimalism
- High-contrast industrial utility
- Editorial product narrative
- Precision-driven geometric design
- Controlled density dashboard system
- Quiet luxury interface
- Structured data-first layout

Avoid generic AI aesthetics, overused layouts, and design clichés.

---

## 6.2 Motion & Interaction

- Use **Angular Animations** (`@angular/animations`) for component transitions
- CSS-first animations for simple effects
- Staggered entry using `query()` and `stagger()`
- Use `provideAnimationsAsync()` in bootstrap for deferred animation loading
- Scroll-triggered enhancements via `IntersectionObserver`
- No excessive animation noise

---

## 6.3 Spatial & Visual Discipline

- Grid-based flexible systems (CSS Grid + Flexbox)
- Intentional whitespace using SCSS spacing tokens
- Visual hierarchy clarity with layered depth
- No visual clutter or default flat backgrounds
- SCSS variables and mixins for a consistent design token system

---

# 7. SCALABILITY MINDSET (BILLION-USER STANDARD)

Every solution must assume high traffic, global usage, large engineering teams, and continuous iteration.

Angular-specific performance requirements:

- Standalone components everywhere
- `OnPush` change detection on all components
- Signals for all local and shared reactive state
- `@defer` for all heavy or below-the-fold UI sections
- Lazy loading via `loadComponent` / `loadChildren`
- Bundle optimization via Angular CLI build budgets
- `providedIn: 'root'` for tree-shakeable services
- `provideHttpClient(withFetch())` for Fetch API-based HTTP

---

# 8. STRICTLY PROHIBITED

- `*ngIf`, `*ngFor`, `*ngSwitch`, `[ngSwitch]` in new code
- `@Input()` / `@Output()` decorators in new code (use `input()`, `output()`, `model()`)
- Constructor-based dependency injection (use `inject()`)
- NgModules in new features (use Standalone)
- `any` type usage
- Business logic inside component templates
- Direct HTTP calls inside components
- Mutable shared state without Signals or NgRx Signal Store
- Missing `track` expression in `@for` blocks
- Observable memory leaks (missing `takeUntilDestroyed()` or `async` pipe)
- Generic AI aesthetics and cookie-cutter SaaS layouts
- Untested components, services, pipes, and directives
- `console.log` in production code

---

# 9. REQUIRED OUTPUT STRUCTURE

When generating implementations, always include:

1. Standalone component folder structure
2. Typed components with `OnPush` + Signal-based inputs/outputs
3. Services using `inject()` and `HttpClient`
4. Signals for all reactive state; RxJS only for streams
5. `@if`, `@for`, `@switch`, `@let`, `@defer` used appropriately
6. SCSS styles modularized with design tokens
7. Unit tests for every component, service, pipe, and directive
8. Clear architectural explanation
9. Design direction rationale
10. Loading and error state UI per feature route

# Important Rules (MUST FOLLOW FOR EACH IMPLEMENTATION)

1. Before writing any code, describe your approach and wait for approval.
2. If requirements are ambiguous, ask clarifying questions before writing any code.
3. After finishing any code, list edge cases and suggest test cases to cover them.
4. If a task requires changes to more than 3 files, stop and break it into smaller tasks first.
5. When there is a bug, write a test that reproduces it first, then fix until the test passes.
6. Every correction is a learning point — reflect and prevent the same mistake.
7. Always use semantic HTML with unique IDs and ARIA attributes.
8. Always use `@if`, `@for`, `@switch`, `@let`, and `@defer` — never structural directives.
9. Always use `input()`, `output()`, `model()` — never `@Input()` / `@Output()` decorators.
10. Always use `inject()` — never constructor injection.
11. Always use Signals for reactive state — RxJS only for async streams.
12. Always write unit tests for every component, service, pipe, and directive.
13. Maximum lines per component file must not exceed 500 lines.
14. Always use `OnPush` change detection for all components.
15. Always handle Observable cleanup with `takeUntilDestroyed()` or `async` pipe.
16. Always create loading state UI and error state UI for every feature route.
