# Enterprise Frontend Architecture & Design Standard

This skill defines the mandatory standards for building production-grade SaaS interfaces intended for high-scale environments (millions to billions of users).

The objective is to deliver:

- Scalable architecture
- Long-term maintainability
- Performance at scale
- Accessibility compliance
- Test-driven reliability
- Distinct, brand-defining design quality

Every implementation must meet enterprise engineering standards.

---

# 1. NON-NEGOTIABLE ENGINEERING REQUIREMENTS

## 1.1 Framework & Platform Standard

- Framework: **Next.js (React)**
- Language: **TypeScript (strict mode)**
- Rendering Strategy: Choose appropriately (SSR, SSG, ISR, RSC) based on scalability and performance needs.
- No alternative frameworks.

---

## 1.2 Architectural Discipline

All implementations must follow:

### SOLID Principles

- Single Responsibility
- Open/Closed
- Liskov Substitution
- Interface Segregation
- Dependency Inversion

### ACID-Inspired Frontend Consistency

- Atomic component design
- Isolated logic
- Predictable state management
- Deterministic rendering behavior
- Durable and extensible patterns

### Separation of Concerns

Clear modular boundaries:

```
/components
/features
/hooks
/services
/utils
/types
/styles
/__tests__
```

Requirements:

- No business logic inside presentational components
- No direct API calls inside UI components
- Reusable abstractions must be extracted
- No monolithic components
- No tight coupling
- Clear dependency direction

---

## 1.3 Code Quality Standards

- Strict TypeScript (no `any`)
- Fully typed props, responses, and utilities
- No dead code
- No console logs in production code
- Clean imports
- Re-render optimization awareness
- Performance-safe patterns
- Error boundaries where necessary
- Defensive programming mindset

Code must be readable, scalable, and maintainable for large engineering teams.

---

# 2. ACCESSIBILITY & SEMANTIC HTML (MANDATORY)

Accessibility is not optional.

## 2.1 Semantic Structure

Use semantic HTML elements:

- `<main>`
- `<section>`
- `<article>`
- `<nav>`
- `<header>`
- `<footer>`
- `<aside>`
- `<form>`
- `<button>`

Avoid non-semantic containers when a semantic alternative exists.

---

## 2.2 ARIA & Identifiers

Requirements:

- Every `<section>` must include:
  - `aria-label`
- Every interactive element must include:
  - Unique `id`
  - Unique `aria-label`
- IDs must be:
  - Content-specific
  - Context-aware
  - Globally meaningful
  - Never generic (no `btn1`, `section2`, etc.)

---

## 2.3 Accessibility Compliance

Must ensure:

- Proper heading hierarchy (h1 → h6)
- Keyboard navigability
- Visible focus states
- Screen reader compatibility
- No div-based interactive elements
- ARIA only when necessary (not overused)
- WCAG-conscious design decisions

Interfaces must be usable at global scale across diverse user groups.

---

# 3. MANDATORY UNIT TESTING

No module may exist without corresponding tests.

## 3.1 Required Stack

- Jest
- React Testing Library

---

## 3.2 Coverage Requirements

Test the following:

- Component rendering
- Props validation behavior
- Conditional UI states
- User interactions
- Edge cases
- Hook behavior
- Utility logic
- Service logic (mocked APIs)

Use the AAA pattern:

- Arrange
- Act
- Assert

Target mindset: minimum 80% meaningful coverage.

Tests must validate behavior — not implementation details.

---

# 4. SaaS-Level Design System Philosophy

This is not template-based UI generation.

Design must reflect:

- Product maturity
- Brand authority
- Scalability
- Global usability

---

## 4.1 Design Direction

Before implementation, clearly define:

### Product Context

- What business problem does this solve?
- Who are the users?
- What is the usage frequency?

### Aesthetic Strategy

Choose a strong, intentional direction:

- Refined enterprise minimalism
- High-contrast industrial utility
- Editorial product narrative
- Precision-driven geometric design
- Controlled density dashboard system
- Quiet luxury interface
- Structured data-first layout

Avoid:

- Trend-driven superficial visuals
- AI-generic layouts
- Overused design clichés

---

## 4.2 Motion & Interaction

Motion must be purposeful and performance-safe.

- CSS-first animations for efficiency
- Motion library only when required
- Staggered entry for clarity
- Intentional hover states
- Scroll-triggered enhancements
- No excessive animation noise

Performance and clarity take precedence over decoration.

---

## 4.3 Spatial & Visual Discipline

- Grid-based but flexible systems
- Intentional whitespace
- Visual hierarchy clarity
- Layered depth where meaningful
- No visual clutter
- No default flat backgrounds

Typography, spacing, and rhythm must feel deliberate and engineered.

---

# 5. SCALABILITY MINDSET (BILLION-USER STANDARD)

Every solution must assume:

- High traffic
- Global usage
- Long-term maintainability
- Large engineering teams
- Continuous iteration
- Accessibility audits
- Performance monitoring

Design and code must survive scale.

---

# 6. STRICTLY PROHIBITED

- Generic AI aesthetics
- Overused default fonts
- Predictable hero sections
- Purple gradient on white backgrounds
- Cookie-cutter SaaS layouts
- Inline unstructured styling
- Logic inside JSX
- Uncontrolled state mutations
- Un-tested components

---

When generating implementations, always include:

3. Hooks (if applicable)
4. Services (if applicable)
5. Utilities
6. Styles (modularized)

9. Design direction rationale

# Importtant Rules (MUST FOLLOW FOR EACH IMPLEMENTATION)

1. Before writing any code, describe your approach and wait for approval(Ask me for approval like terminal command access).
2. If the requirements I give you are ambiguous, ask clarifying questions before writing any code.
3. After you finish writing any code, list the edge cases and suggest test cases to cover them.
4. If a task requires changes to more than 3 files, stop and break it into smaller tasks first.
5. When there's a bug, start by writing a test that reproduces it, then fix it until the test passes.
6. Every time I correct you, reflect on what you did wrong and come up with a plan to never make the same mistake again.
7. Always use semantic HTML with unique IDs and ARIA attributes.
8. Always write unit test cases.
9. The maximum lines of one component should not exceed 500 lines.
10. Always go through the code and check if there are any logical errors.
11. Always go with component based architecture.
12. Always create and use more reusable components.
13. Always create loading.tsx and error.tsx files for every route.
